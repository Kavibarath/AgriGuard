# Deploying AgriGuard

How the live system is put together, and the exact clicks to build it from nothing. Follow the
sections in order: each one needs a value from the one before.

| Part | Runs on | Free-plan facts that matter |
|---|---|---|
| PostgreSQL | **Neon** (AWS Singapore) | 100 CU-hours a month; sleeps after 5 min idle and wakes in about a second |
| API (ASP.NET Core 10) | **Render** web service, Docker (Singapore) | Sleeps after 15 min without requests; waking takes about a minute |
| Agent service (FastAPI + LangGraph) | **Render** web service, Docker (Singapore) | Same as the API. Both share 750 instance-hours a month |
| Language model | **Groq** (OpenAI-compatible API) | Per-minute and per-day token limits; the agent waits out a 429 |
| Web console (React, Vite) | **Vercel** | Static site, always on |
| Phone app | **GitHub Actions** artifact (APK), copied to a GitHub Release | Artifacts are kept 30 days; a Release never expires |

```
 phone (APK) ─┐                       ┌─► Neon PostgreSQL
              ├─► Render: API ────────┤
 Vercel web ──┘     ▲        │        └─► Open-Meteo, Stripe (test mode)
                    │ tools  │ runs
                    │        ▼
                Render: agent service ──► Groq
```

Local development does not change: Ollama stays the default model provider, and the local ports
and URLs (5000, 8000, 5173, 10.0.2.2) are unchanged.

**Secrets.** This guide never asks you to paste a secret into a file in the repository, a chat or
an issue. Secrets go only into the Neon, Render, Vercel, GitHub and Stripe dashboards, or into the
environment of one terminal window that you close afterwards. Two secrets are generated by Render
itself and nobody sees them: the JWT signing key, and the key the API and agent share.

## 1. Neon: the database

### 1.1 Create the project

1. Go to <https://neon.com>, then **Sign up** (GitHub sign-in is fine). No card is needed.
2. **Create project**:
   - Project name: `agriguard`
   - Postgres version: **17** (the local and test version)
   - Cloud provider and region: **AWS, Asia Pacific (Singapore)**
3. On the project dashboard, click **Connect**:
   - Branch `main`, database `neondb`, role `neondb_owner`
   - Turn **Connection pooling off**. The API uses its own pool, and its serializable transactions should
     not run through PgBouncer.
   - Copy the connection string. It looks like
     `postgresql://neondb_owner:PASSWORD@ep-xxxx.ap-southeast-1.aws.neon.tech/neondb?sslmode=require…`

### 1.2 Turn it into the .NET form

Npgsql (the API's driver) takes `key=value` pairs, not a URL. In a text editor that is **not**
inside the repository (Notepad, unsaved), rewrite it as:

```
Host=ep-xxxx.ap-southeast-1.aws.neon.tech;Database=neondb;Username=neondb_owner;Password=PASSWORD;SSL Mode=VerifyFull
```

`SSL Mode=VerifyFull` encrypts the connection and checks Neon's certificate and host name.

This one string is the value of `ConnectionStrings__Default` everywhere below. Keep the Notepad
window open until step 3, then close it without saving.

### 1.3 Create the tables and the demo data (from your own terminal)

Seeding runs only through `dotnet ef database update` (EF Core `UseSeeding`), never when the API
starts, so this step is what fills the database.

1. Open a **new** PowerShell window (not the one running your local API) at `E:\AgriGuard`.
   The variables you set here exist only in this window. Closing it removes them, and your local
   API and user-secrets are untouched.
2. Copy the .NET connection string from Notepad to the clipboard, then run:

```powershell
$env:ConnectionStrings__Default = Get-Clipboard
```

```powershell
$env:ASPNETCORE_ENVIRONMENT = 'Production'; $env:Seed__DemoUsers = 'true'
```

```powershell
dotnet tool restore
```

```powershell
dotnet tool run dotnet-ef database update --project backend/src/AgriGuard.Infrastructure --startup-project backend/src/AgriGuard.Api --configuration Release
```

`Production` keeps your local user-secrets (including your local connection string) out of this
run. `--configuration Release` avoids the Debug binaries your running API locks. The output ends
with `Done.` The first run takes a minute or two: it applies every migration, then seeds.

3. Close this PowerShell window.

**If it cannot connect** (a timeout, or a certificate error from the firewall), your network is
blocking or intercepting port 5432. Don't weaken the SSL mode. Use the GitHub fallback instead:

1. GitHub → repository → **Settings → Secrets and variables → Actions → Secrets → New repository secret**:
   name `NEON_CONNECTION_STRING`, value the .NET connection string.
2. **Actions → db-migrate → Run workflow** (branch `main`, "seed demo data" ticked).
3. When it is green, delete the secret again if you like. Both routes are idempotent.

### 1.4 Check it: the PostgreSQL deployment evidence

In Neon: **SQL Editor**, database `neondb`. Run:

```sql
select count(*) as tables from information_schema.tables where table_schema = 'public';
```

```sql
select email, role from users where email like '%@agriguard.demo' order by email;
```

```sql
select migration_id from "__EFMigrationsHistory" order by migration_id;
```

Expect 34 tables, the 10 demo accounts, and every migration. **Screenshot each result**, plus
**Tables** in the sidebar and the project dashboard showing the region. That is the PostgreSQL
deployment evidence.

Optional: **Settings → Compute**: keep the autoscaling maximum at 1 CU or less. Small computes
stretch the 100 CU-hours furthest.

## 2. Groq: the language model

1. Go to <https://console.groq.com>, then **Sign up**. No card is needed.
2. **API Keys → Create API Key**, name it `agriguard-render`, and copy it. It is shown once, so paste it
   straight into Render in step 3 (or into the Notepad window for a moment).
3. **Settings → Limits**: the deployment uses `qwen/qwen3.8-27b` (30 requests and 8K tokens a
   minute, 200K tokens a day on the free plan), with reasoning switched off
   (`AGENT_LLM_REASONING_EFFORT=none`) so every token goes into the answer. One agent run makes
   roughly 6 to 10 model calls; when a minute's 8K tokens are used up, the agent waits as Groq
   asks and carries on, so a run can take a minute or two. The daily limit allows a good number of
   runs a day: plenty for marking and the viva, not for load testing.

   If that model is ever missing from your Limits page, use `openai/gpt-oss-120b` instead, with
   `AGENT_LLM_REASONING_EFFORT` = `low` (gpt-oss has no `none`).

The agent talks to Groq through the OpenAI-compatible API (`/chat/completions` with JSON mode).
Each reply is still validated against the Pydantic schema and repaired at most twice, exactly as
with Ollama.

**Fallback: Gemini.** If Groq is unavailable, create a key in Google AI Studio and change three
values on the agent service (step 3.4): `AGENT_LLM_BASE_URL` =
`https://generativelanguage.googleapis.com/v1beta/openai`, `AGENT_LLM_MODEL` = a current Flash model
ID from AI Studio, and `AGENT_LLM_API_KEY` = the Gemini key. Gemini has not been tried with
AgriGuard. If its runs fail with a 400 about `response_format`, tell me.

## 3. Render: the API and the agent service

The repository's `render.yaml` (a Render *Blueprint*) describes both services: Docker builds,
the Singapore region, the health checks and every environment-variable **name**.

### 3.1 Apply the Blueprint

1. Go to <https://render.com>, then **Sign up with GitHub** as Kavibarath. No card is needed.
2. **New + → Blueprint**. Connect the GitHub account and give Render access to `Kavibarath/AgriGuard`.
3. Pick the repository, then branch **main**. Blueprint name: `agriguard`. Render reads `render.yaml` and
   lists two services, `agriguard-api` and `agriguard-agent`.
4. Render asks for every value marked `sync: false`. The public URLs don't exist yet, so enter
   placeholders now and replace them in 3.3:

| Service | Variable | Enter now |
|---|---|---|
| agriguard-api | `ConnectionStrings__Default` | the .NET connection string (1.2) |
| agriguard-api | `AgentService__BaseUrl` | `https://pending.invalid` |
| agriguard-api | `Cors__AllowedOrigins__0` | `https://pending.invalid` |
| agriguard-api | `Payments__PublicBaseUrl` | `https://pending.invalid` |
| agriguard-api | `Payments__Stripe__SecretKey` | leave empty (card payments off; see step 7) |
| agriguard-api | `Payments__Stripe__WebhookSecret` | leave empty |
| agriguard-agent | `AGENT_LLM_API_KEY` | the Groq key (2) |
| agriguard-agent | `AGENT_API_BASE_URL` | `https://pending.invalid` |

5. **Apply**. Render builds both Docker images. The API takes about 5–8 minutes the first time, and
   the agent about 3.

You never type `Jwt__SigningKey`, `AgentService__ApiKey` or `AGENT_API_KEY`. Render generates the
first two, and the agent's key is read from the API's (`fromService`), so they always match.

### 3.2 Check both services are up

Each service's page shows its URL at the top (`https://agriguard-api.onrender.com` or similar;
Render adds a suffix if the name is taken). Note `API_URL` and `AGENT_URL`. Then open:

- `API_URL/health/live` → `{"status":"Healthy",…,"checks":[]}` (the process is up)
- `API_URL/health` → `"status":"Healthy"` with a `database` check (the API reaches Neon)
- `API_URL/swagger` → the API reference
- `AGENT_URL/health/live` → `{"status":"healthy"}`
- `AGENT_URL/health` → `"provider":"openai-compatible"`, `"model":"qwen/qwen3.8-27b"`, `"llmReachable":true`

If the API's deploy fails, open **Logs**. A startup refusal names the setting. For example,
`Jwt:SigningKey must decode to at least 32 bytes` means the generated key didn't suit: set
`Jwt__SigningKey` by hand under **Environment**, using the output of `openssl rand -base64 32`
(Git Bash).

`llmReachable: false` means the Groq key is wrong or missing: check `AGENT_LLM_API_KEY`.

### 3.3 Replace the placeholders

**agriguard-api → Environment → Edit:**

- `AgentService__BaseUrl` = `AGENT_URL`
- `Payments__PublicBaseUrl` = `API_URL`. Stripe sends the payer back to the API's `/payments/return` page.
- `Cors__AllowedOrigins__0`: leave the placeholder until step 4 gives you `WEB_URL`.

**agriguard-agent → Environment → Edit:**

- `AGENT_API_BASE_URL` = `API_URL`

**Save, rebuild, and deploy** on each. Each service redeploys in a minute or two.

### 3.4 What each variable is (names only)

**API** (`agriguard-api`). ASP.NET Core maps `__` to `:`, so `Jwt__SigningKey` is `Jwt:SigningKey`.

| Variable | Secret? | Value |
|---|---|---|
| `ConnectionStrings__Default` | yes | Neon, .NET form, `SSL Mode=VerifyFull` |
| `Jwt__SigningKey` | yes (generated) | base64 of 32 random bytes |
| `AgentService__ApiKey` | yes (generated) | shared with the agent's `AGENT_API_KEY` |
| `AgentService__BaseUrl` | no | `AGENT_URL` |
| `AgentService__DispatchTimeout` | no | `00:01:30`, long enough to wake a sleeping agent |
| `Cors__AllowedOrigins__0` | no | `WEB_URL` |
| `Payments__PublicBaseUrl` | no | `API_URL` |
| `Payments__Stripe__SecretKey` | yes, optional | `sk_test_…` only (live keys are refused) |
| `Payments__Stripe__WebhookSecret` | yes, optional | `whsec_…` |
| `ForwardedHeaders__Enabled` | no | `true`: trust Render's `X-Forwarded-Proto`/`-For` (last hop only) |
| `Swagger__Enabled` | no | `true` |
| `Calendar__TimeZone` | no | `Asia/Colombo` |
| `OpenMeteo__BaseUrl` | no | `WEB_URL/openmeteo/` (the Vercel relay; unset calls Open-Meteo directly) |
| `Seed__DemoUsers` | no | `true` (used only by `dotnet ef database update`) |
| `PORT` | set by Render | the container binds to it (`ASPNETCORE_HTTP_PORTS`) |

**Agent** (`agriguard-agent`):

| Variable | Secret? | Value |
|---|---|---|
| `AGENT_API_KEY` | yes (from the API) | same as `AgentService__ApiKey` |
| `AGENT_API_BASE_URL` | no | `API_URL` |
| `AGENT_LLM_PROVIDER` | no | `openai-compatible` (local default: `ollama`) |
| `AGENT_LLM_BASE_URL` | no | `https://api.groq.com/openai/v1` |
| `AGENT_LLM_API_KEY` | yes | the Groq key |
| `AGENT_LLM_MODEL` | no | `qwen/qwen3.8-27b` |
| `AGENT_LLM_REASONING_EFFORT` | no | `none` (`low` for gpt-oss) |
| `PORT` | set by Render | uvicorn binds to it |

## 4. Vercel: the web console

1. Go to <https://vercel.com>, then **Sign up with GitHub** (Hobby plan, free).
2. **Add New… → Project → Import** `Kavibarath/AgriGuard`.
3. Configure:
   - **Root Directory**: `web` (click **Edit** next to it)
   - Framework preset: **Vite** (also set by `web/vercel.json`); build `npm run build`, output `dist`
   - **Environment Variables**: `VITE_API_BASE_URL` = `API_URL`
4. **Deploy**. About 1–2 minutes. Note the production domain, for example `https://agriguard.vercel.app`.
   That is `WEB_URL`. (A different name can be chosen under **Settings → Domains**.)

`VITE_API_BASE_URL` is baked in at build time. If it changes, **Deployments → ⋯ → Redeploy**.
`web/vercel.json` rewrites every path to `index.html`, so a refresh on `/cases/…` or `/agent-runs/…`
works.

### 4.1 Allow the web console to call the API, and route the weather through Vercel

Render → **agriguard-api → Environment**, then save and deploy:

- `Cors__AllowedOrigins__0` = `WEB_URL` (exactly, `https://`, no slash)
- `OpenMeteo__BaseUrl` = `WEB_URL/openmeteo/` (**with** the slash at the end)

Why the second one: Open-Meteo's free API limits each IP address, and Render's free services share
their outgoing addresses with many other customers. On 6 Oct 2026 every forecast request from
Render got `429 Too Many Requests`, so V8 (weather) was "not evaluated" and the spray-window panel
said "forecast unavailable". `web/vercel.json` relays exactly one path, `/openmeteo/v1/forecast`,
to `https://api.open-meteo.com/v1/forecast`, so Open-Meteo sees Vercel's address instead. Nothing
else is relayed.

Check the weather: as any signed-in user, the dashboard's spray-window panel shows days, not
"forecast unavailable". Or open `WEB_URL/openmeteo/v1/forecast?latitude=7&longitude=80.8&hourly=temperature_2m`
in a browser: it returns JSON.

Check: open `WEB_URL`, choose **Sign in**, and sign in as `admin@agriguard.demo`. The dashboard loads
with data. A CORS error in the browser console means the origin doesn't match exactly.

## 5. GitHub: the Android APK

1. GitHub → repository → **Settings → Secrets and variables → Actions → Variables → New repository variable**:
   - `API_BASE_URL` = `API_URL`
   - `AGENT_BASE_URL` = `AGENT_URL` (for the warm-up workflow)
2. **Actions → ci-mobile → Run workflow** on branch `main`. It analyzes, tests, then builds
   `flutter build apk --release --dart-define=API_BASE_URL=<API_URL>` in about 6–10 minutes.
3. Open the finished run, and under **Artifacts** download **agriguard-mobile-apk** (a zip holding
   `app-release.apk`).
4. Make it permanent (artifacts expire after 30 days): **Releases → Draft a new release**:
   - tag `v1.0.0`, title "AgriGuard 1.0 (SE3090 submission)"
   - attach `app-release.apk`, then **Publish release**
   - the APK's link on the release page is the submission's download link.

### Installing the APK (for the submission)

1. On an Android phone (Android 7 or later), open the release link and download `app-release.apk`.
   Or copy it over USB.
2. Open the downloaded file. Android asks to **allow installs from this source** (the browser or
   Files app): **Settings → Allow from this source**, then go back.
3. **Install**. If Play Protect warns about an unknown developer: **More details → Install anyway**.
   The APK is signed with a build key, not a Play Store key.
4. Open **AgriGuard** → **Sign in** as `farmer@agriguard.demo`. The first sign-in after a quiet
   period can take up to a minute while the API wakes (see section 8).

If an older AgriGuard is installed, **uninstall it first**. Each CI build is signed with a fresh
key, so Android refuses to update over a different build ("App not installed").

## 6. Wake-up and keep-alive

Free Render services sleep after 15 minutes without requests, and waking takes about a minute.
The phone gives up on a request after 30 seconds, so **wake the system before anyone uses it**:

- **Before the viva or a demo** (3 minutes ahead): **Actions → warm-up → Run workflow**. Or open
  `API_URL/health` and `AGENT_URL/health` in a browser and wait for both to answer. Then sign in on
  the web once. Keep using it, and nothing sleeps.
- **Before the marking window**, if you know when it is, do the same.

**Don't run a permanent keep-alive** (a cron ping every 10 minutes):

- Render gives **750 instance-hours a month for the whole workspace**. Two services kept awake
  around the clock need about 1,490, so the free hours would run out in the middle of the month,
  and Render then **suspends both services until the 1st**. That would break the live system
  before 21 Oct.
- A permanently awake API also keeps Neon awake (the API's background jobs query every minute).
  That would use up Neon's 100 CU-hours, and Neon then suspends the database for the month.

That is why `warm-up.yml` runs only when you click it.

## 7. Optional: card payments (Stripe test mode)

Cash payment works with no setup. For card payments:

1. Stripe Dashboard, in the **sandbox** (test mode): **Developers → API keys** → copy the secret key `sk_test_…`.
2. Render → agriguard-api → Environment: `Payments__Stripe__SecretKey` = that key. Save and deploy.
   Live keys are refused at startup.
3. Webhook (optional: the return page and the app also confirm payments). In **Developers → Webhooks →
   Add destination**:
   - Endpoint URL: `API_URL/api/payments/stripe/webhook`
   - Events: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.expired`
   - Create it, reveal the **signing secret** `whsec_…`, and set it as `Payments__Stripe__WebhookSecret` on
     agriguard-api. Save and deploy.
4. Test card: `4242 4242 4242 4242`, any future date, any CVC.

## 8. Smoke test of the live system

Warm up first (section 6). Accounts and plots are in the README's "Demo accounts". Tick each one:

- [ ] **Web sign-in**: `WEB_URL` → Sign in as `agronomist.anu@agriguard.demo`. The dashboard shows tiles and the spray-window panel.
- [ ] **Phone report**: on the phone, as `farmer@agriguard.demo`, report a problem on **A-01** (tomato) with symptoms, GPS and an optional photo.
- [ ] **AI advice (hosted model)**: **Get AI advice**. On the web, `/agent-runs` shows the run move through
      Planning → Diagnosing → Triaging → Drafting → Validating. It reaches **PendingApproval** in well
      under a minute with Groq, or ends **Escalated** with farmer advice when no treatment is possible.
      Both are correct outcomes. `AGENT_URL/health` shows which model served it (`qwen/qwen3.8-27b`).
- [ ] **Agronomist approval**: approve it on the web. The phone shows the prescription (RX-…) with the do-not-harvest date.
- [ ] **Order and payment**: as `dealer.anu@agriguard.demo`, the order appears under `/orders`. Pack it, and
      record a **cash** payment (or pay by card on the phone if Stripe is set up).
- [ ] **Hand-over**: Hand over with the pickup code shown on the phone. The order is Collected on both sides.
- [ ] **Booking**: on the phone, **Harvest** on **A-02** (onion) → pick a day → book a collection slot (BK-…).
- [ ] **Check-in**: on the web as the agronomist, `/collection-planner` → the booking → **Check in**,
      then **Record weight**. The phone shows "Delivered X kg".

If the AI step fails, open the run on `/agent-runs/…`: the failure reason is recorded. A
`429`/rate-limit reason means Groq's per-minute limit was hit; wait a minute and start a new run.

## 10. Redeploying after a change

- Push or merge to `main`. Render redeploys both services and Vercel redeploys the web
  automatically.
- A new EF migration also needs section 1.3 again (or the `db-migrate` workflow), **before** the
  new API version goes live.
- A new APK needs the ci-mobile workflow (it runs on every push to `main`). Download the new
  artifact, and replace the file on the Release.
